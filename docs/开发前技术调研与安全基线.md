# 开发前技术调研与安全基线

调研日期：2026-11-12

本文基于仓库中的《吉他谱识别与 GPX 生成网站开发计划.docx》整理，目标是在写业务代码前固定技术门禁、开源选型和上传安全边界。网站和服务器部署不在本次范围内。

产品决策：2026-11-12 已确认 MVP 只交付 alphaTab 生成的 `.gp`，面向 Guitar Pro 7/8。GPX 不纳入首版范围。

## 结论

不要先搭建完整产品页面。首先验证一条最小闭环：

```text
PDF/图片 -> 隔离预处理 -> OMR -> MusicXML -> Score IR -> GP -> 回读
```

这条链路通过兼容性样本后，再投入页面排序、校对编辑器和任务系统。上传链路必须从第一天按不可信输入设计，不能等到上线前再补。

MVP 使用 alphaTab 直接写 `.gp`，不维护 GPX 适配器。Guitar Pro 6 及更早版本不在兼容范围内。

### GPX 技术背景

alphaTab 1.9.0 的 `Gp7Exporter` 明确写出 Guitar Pro 7+ 的 `.gp`，而 `GpxImporter` 只负责读取 GPX。ScoreTranslate 则是先调用 alphaTab 的 GP7 写出器，再转换其 GPIF XML、封装为 BCFS 并做 BCFZ 压缩，最终得到 GP6 的 `.gpx`。该路径仅作为技术调研记录，不进入 MVP。

ScoreTranslate 的 GPX 写出有三个已知边界：

- 每个内部文件约 3.85 MiB 上限，超过时明确拒绝。
- 多谱表会拆成独立音轨。
- GP7/8 音频伴奏、RSE 音色与部分轨内音色切换不会保留。

如果未来恢复 Guitar Pro 6 支持，GPX writer 必须作为独立适配器维护，不能让页面、Score IR 或 OMR 代码依赖其容器细节。

### GP 兼容性

`.gp` 是 Guitar Pro 7 引入的现代工程格式。Guitar Pro 7 和 8 使用 `.gp`，Guitar Pro 6 及更早版本不能读取。

alphaTab 的 `Gp7Exporter` 在容器内写入 `VERSION=7.0`，但当前 `GpifWriter` 同时写入 `GPVersion=8.1.3` 和 `EncodingDescription=GP8`。因此：

- 对 Guitar Pro 8 的兼容性最有把握，但仍需用真实桌面端打开、播放、保存和再次打开。
- GPIF 元数据带 GP8 标识，不能仅凭 `.gp` 扩展名或 `VERSION=7.0` 承诺 Guitar Pro 7 一定无警告打开。
- alphaTab 自身可以读取 GP3-GP8，但对 alphaTab 的回读通过只能证明格式可解析，不能替代 Guitar Pro 7/8 实机测试。
- 若产品明确承诺 Guitar Pro 7，应建立独立的 GP7 兼容档，并在发布前修正或验证 GP8 专用元数据和能力。

对本项目而言，`.gp` 是唯一首发输出格式，兼容路径比自制 GPX 更稳。Guitar Pro 6 及更早版本不在产品承诺范围内。

## 推荐开发基线

控制面仍采用开发计划中的 Next.js + FastAPI + PostgreSQL + Celery。上传二进制不经过应用 API，而是由控制面签发短期上传凭证，客户端直接写入私有对象存储的隔离区。

处理链路按职责拆分：

1. 控制面校验任务配额、文件数量、声明大小和用户权限，生成随机对象键及短时上传凭证。
2. 客户端直接上传到 quarantine 前缀。上传完成后，服务端读取对象元数据并复核真实大小、校验和和文件类型。
3. 隔离 Worker 下载原文件，检查 PDF 页数和图像像素数，再执行解码、纠偏和重新编码。原文件不对浏览器提供预览。
4. OMR、排序和转换在无公网出口、非 root、只读根文件系统的独立执行环境中运行，并限制 CPU、内存、进程数、磁盘、执行时间和输出大小。
5. 只把重新生成的无害预览图、结构化结果和导出文件写入可下载区域。下载继续使用短时签名 URL，并强制 `Content-Disposition: attachment`。
6. 原始文件、中间产物和导出文件按不同生命周期自动删除，默认不晚于任务完成后 24 小时。

如果部署资源允许，处理恶意文件的边界优先使用 microVM 或 gVisor。单独一个普通 Docker 容器不能被视为强安全边界，因为文件解析器漏洞可能导致容器逃逸或共享内核攻击。

## 上传与文件处理安全要求

采用 [OWASP File Upload Cheat Sheet](https://cheatsheet.owasp.org/cheatsheets/File_Upload_Cheat_Sheet/) 的纵深防御思路，至少落实以下控制。

| 风险 | 必须采取的控制 |
| --- | --- |
| 伪装文件、双扩展名 | 只允许业务需要的扩展名；同时检查魔数、容器结构和完整解码结果，不信任扩展名、浏览器 MIME 或用户文件名 |
| 路径覆盖与目录穿越 | 对象键完全由服务端生成；用户文件名只作为严格限长的元数据，不参与磁盘路径 |
| 越权读取他人任务 | 每个 API 同时校验身份、租户和任务归属；任务 ID 使用不可枚举随机值，但不能把 ID 当唯一权限 |
| CSRF 与上传滥用 | Cookie 会话使用 `SameSite`、CSRF token 或同源校验；登录用户按账号限流，匿名入口必须有会话级与 IP 级配额 |
| 图片炸弹、超大图像 | 限制解码后总像素、宽高、帧数和每任务页数；HEIC 等高风险格式只在上线必需时启用 |
| PDF bomb、恶意 PDF 功能 | 限制真实页数和渲染总像素；拒绝或忽略嵌入附件、JavaScript、Launch action；只在隔离进程中使用 qpdf/pdfcpu 与渲染器 |
| 解析器漏洞和容器逃逸 | 处理 Worker 使用最新固定版本、非 root、无网络、seccomp/AppArmor、资源限额和短生命周期；高风险阶段优先 microVM |
| 恶意内容再次分发 | 原文件不直接回传；预览必须由服务端解码后重新编码，并清除 EXIF、GPS、XMP 和嵌入对象 |
| 存储桶被公开访问 | 原文件、中间产物和结果桶均保持私有，开启服务端加密和公开访问阻断；隔离区与成品区分离 |
| 签名 URL 泄露 | URL 短时有效；不写日志、埋点、错误详情或 Referer；下载文件名由服务端生成 |
| 放大攻击与队列耗尽 | 上传前限额、全局并发上限、用户并发配额、每阶段超时和自动重试上限；不得无限重试 |
| 已知恶意样本 | ClamAV 可作为独立扫描服务，但必须在无害化之前执行，并与重编码/结构校验组合使用 |
| 依赖供应链 | 固定版本与锁文件、生成 SBOM、做许可证清单和漏洞扫描；尤其是 PDF、图像、压缩和 OMR 解析依赖 |

### 格式策略

首轮技术门禁建议只启用手工指定白名单：PDF、JPEG、PNG、WebP。HEIC 涉及额外的容器和编解码解析面，等主链路稳定、隔离方案验证后再加入。拒绝 ZIP 和其他归档格式，避免压缩炸弹和多类型内容混装。

PDF 只作为一次性输入。系统渲染出页面图后，后续识别、预览和下载都使用重新生成的无害图片，不把原始 PDF 放回浏览器，也不允许 PDF.js 执行其中的主动内容。

### 认证与匿名使用

如果 MVP 允许匿名试用，需要由服务端签发短期、不可枚举的匿名任务凭证，并叠加 IP、会话、UA 风险评分、验证码和严格配额。匿名凭证只解决任务隔离，不能替代正式账号体系。若公开试点会长期运行，应优先确定登录方式，而不是把匿名上传作为长期方案。

## Score IR 与导出边界

alphaTab 的 `Score` 模型适合预览、播放和 `.gp` 写出，但不能直接充当唯一 Score IR，因为它没有开发计划要求的来源页、坐标、置信度和 revision 语义。

建议保留自定义 Score IR，并建立单独的 alphaTab 导出适配器：

- `Score IR -> alphaTab Score`：Web 预览、播放以及 Guitar Pro 7/8 `.gp` 输出。

导出器只使用不可变快照，不能修改编辑器中的主模型。导出完成后立即用 alphaTab 回读，并记录音轨、调弦、音高、时值、弦品和技巧的降级项；最终兼容性以 Guitar Pro 7/8 桌面端测试为准。

## 页面排序修正

开发计划中的“大于 8 页使用有约束的旅行商问题或动态规划”需要调整。30 页的精确哈密顿路径搜索空间过大，不适合在线任务。

首版应使用可解释的候选图：

1. 用小节号连续性、页眉页脚、谱表结构、调号/拍号、文件名和 EXIF 建立有向边。
2. 用束搜索生成若干候选完整顺序。
3. 用 2-opt、or-opt 或受时间限制的局部搜索改善总成本。
4. 输出 `suggest_order`、`confidence` 和逐边理由。
5. 低置信度、断号或循环冲突直接要求用户确认，不静默自动提交。

OR-Tools 可以作为后续优化器，但首版自研候选评分和束搜索更容易解释、测试和校准。

## 第一阶段技术门禁

第一阶段只做可测量、可回读的验证，不追求完整 UI。

| 顺序 | 工作 | 退出条件 |
| --- | --- | --- |
| 1 | 准备 50 页许可清晰样本，并记录调弦、谱表类型、技巧、页序和问题类型 | 评测说明可复现，训练/评测数据无许可争议 |
| 2 | 对 Audiveris、商业 OMR 和至少一个标准谱面无 TAB 的开源基线做同集测试 | 有 Note F1、TAB 保留率和结构错误分类 |
| 3 | 完成 PDF 页数限制、图片像素限制、重编码和隔离 Worker 原型 | 恶意/畸形样本均只能失败，不能越权、联网或耗尽主机 |
| 4 | 完成 Score IR -> alphaTab Score -> GP 写出并用 alphaTab 回读 | 30 份样本无致命结构错误 |
| 5 | 在 Guitar Pro 7/8 打开、播放、保存并再次打开样本 | 输出兼容性矩阵和全部降级项 |
| 6 | 评估 10 页任务资源、时延、成本和并发 | 可给出继续、换 OMR、换输出格式或停止的书面决定 |

## 开工前需要用户确认的事项

以下问题不会阻止安全上传底座和 GP 格式适配器的开发，但会影响最终产品承诺：

1. MVP 是否允许匿名试用；如果允许，每日任务数和单任务总大小上限是多少。
2. 是否允许商业 OMR 服务处理用户文件，是否要求所有内容只在自托管环境处理。
3. 首发是否只做单首吉他谱，还是必须支持多轨乐队谱。

默认按开发计划推进：输出 `.gp`、兼容 Guitar Pro 7/8、允许人工确认页面顺序、文件不用于训练、首发单首吉他谱。
