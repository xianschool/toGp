# 六线谱来源与格式兼容策略

## 结论

根据输出软件或出版来源选择识别策略，比继续逐张打补丁更可靠。但不应把目标定义成“为每一款软件写一套识别器”，也不要仅依赖 PDF 元数据判断品牌。

更合适的做法是两级判断：

1. **渲染类型**：决定采用哪套基础解析流程。
2. **来源家族**：在渲染类型之上选择细节规则和校验器。

推荐的基础分类是：

| 类型 | 特征 | 主要处理方式 |
|---|---|---|
| 矢量文本谱 | 数字、歌词、和弦名是可提取文本，弦线是矢量路径 | 直接读取文字坐标和线条 |
| 矢量轮廓谱 | 数字和符号被转换为路径，PDF 中没有字符 | 局部栅格化后 OCR |
| 数字截图 | PNG/JPEG 或网页截图，边缘清晰但无源文件信息 | 图像切分、OCR、视觉规则 |
| 扫描印刷谱 | 有透视、噪声、纸张纹理和不均匀光照 | 去噪、纠偏、二值化、版面校正 |
| 混排谱 | 五线谱、六线谱、歌词、和弦图、标题说明同时存在 | 分层识别并按系统关联 |

“来自 Guitar Pro、MuseScore 或 Sibelius”属于第二层信息。品牌不能代替渲染类型判断，因为同名软件可能导出文本 PDF、轮廓 PDF，用户还可能打印后再扫描。

## 为什么品牌判断仍然有价值

同一家族的谱面通常具有稳定的排版习惯：

- 六线谱与五线谱的相对位置；
- 默认弦距和小节线宽度；
- 节奏符干、符尾和休止符的画法；
- 和弦图尺寸、弦线数量和指法点样式；
- 技巧标记使用文字、字体字形还是曲线路径；
- 标题、作者、页码和版权文字的布局；
- PDF 内嵌字体和字体子集命名。

因此来源分类可以：

- 选择更合适的弦线检测阈值；
- 决定小数节线是矩形还是零宽路径；
- 选择正确的歌词行；
- 判断 `X` 是闷音还是“按和弦图演奏该弦”；
- 使用不同的小节编号、重复记号和反复结构规则；
- 在识别前消除五线谱、文字说明等干扰层。

## 已识别的两类实际样本

### 1. 超大幅矢量 PDF

样本特征：

- 五线谱与六线谱上下成对出现；
- 六弦线是浅灰色矢量路径；
- 部分弦线左端被短路径裁断；
- 小节线为约 4.5pt 的实心矩形；
- 音符竖线是零宽路径；
- 中文标题和作者使用 PingFang 字体；
- 中文段落文字不是粗体；
- `X` 在和弦图有效时表示按和弦指法演奏对应弦。

这类文件可以非常准确地恢复弦号、品位、小节和段落，但必须：

- 合并同一水平线上的所有短路径；
- 区分矩形小节线与零宽符干；
- 合并反复记号附近的双小节线；
- 从字体和字号提取中文标题；
- 将 X 结合当前和弦图转换为实际品位。

### 2. 数字六线谱截图

样本特征：

- 灰黑色五线谱与六线谱混排；
- 和弦名和和弦图为红色；
- 同一小节存在单行、双行歌词；
- 六线谱中大量 `X` 作为和弦扫弦占位；
- 和弦图是六弦、四品或五品的小网格；
- 页与页之间没有 PDF 元数据可判断来源。

这类文件不能靠元数据识别，需要视觉规则：

- 红色连通域定位和弦名；
- 网格线定位和弦图；
- 指法圆点映射为（弦，品）；
- 将 X 替换成当前和弦对应弦的品位；
- 按小节编号而不是仅按竖线校验小节数量；
- 区分歌词、技巧文字和段落标题。

## 软件与平台范围

“所有能打印六线谱的软件”是持续变化的市场，无法形成永久封闭列表。应维护来源目录，并按优先级增加适配器。

### 专业制谱软件

| 软件 | 六线谱能力 | 常见来源特征 | 优先级 |
|---|---|---|---|
| Guitar Pro 7/8 | 核心能力，原生 GP 格式 | GP 字体、弦距、技巧和和弦图布局较统一；PDF 可能含文字或轮廓 | P0 |
| MuseScore Studio | 免费开源，支持 TabStaff | 常见 Leland/Bravura/Edwin 字体；支持 PDF、SVG、PNG | P0 |
| Dorico | 专业制谱，SMuFL 字形体系 | Bravura 等 SMuFL 字体；高精度排版 | P1 |
| Sibelius | 专业制谱 | Opus/Inkpen 字体和特有的文字/图形布局 | P1 |
| Finale | 专业制谱 | Maestro 字体及旧版布局习惯 | P1 |
| Notion | 桌面与移动制谱 | 自有触摸编辑布局，PDF 需要样本确认 | P2 |
| StaffPad | 手写识别与制谱 | 输出样本少，布局依导入模板变化 | P2 |
| Overture / Encore / Harmony Assistant / Melody Assistant / PriMus / Capella | 较小型或历史制谱软件 | 各自字体、符号映射和旧式排版 | P2 |

### 六线谱专用工具

| 软件 | 特征 | 优先级 |
|---|---|---|
| TuxGuitar | Java 桌面应用，兼容多种吉他谱格式 | P1 |
| TablEdit | 强调六线谱、印刷和 1–12 弦乐器 | P1 |
| Power Tab Editor | 历史二进制格式，主要面向吉他/贝斯 | P2 |
| alphaTab | Web/JS 渲染器，SVG、Canvas 或截图 | P1 |
| VexTab / VexFlow | 浏览器矢量渲染或截图 | P2 |
| Soundslice | Web 渲染，可显示六线谱、和弦名和指法 | P1 |
| Flat | Web/桌面/移动，支持吉他谱和 PDF 导入 | P1 |
| Songsterr | Web/App 六线谱播放器，通常通过截图或打印获得 | P1 |
| Ultimate Guitar | Web 与移动端，谱面样式和广告布局不完全稳定 | P2 |

### 排版系统

| 系统 | 特征 | 优先级 |
|---|---|---|
| LilyPond / Frescobaldi | Emmentaler 字形，PDF 元数据和路径特征明显 | P1 |
| Denemo | LilyPond 后端，可能继承 LilyPond 输出特征 | P2 |
| Sibelius/Dorico 的出版物导出 | 可能经过出版机构二次排版 | P1 |

### 出版物和非软件来源

出版物不一定保留生成软件的版面。还可能经过：

- InDesign、Illustrator 或页面排版软件；
- 扫描仪、打印机或复印机；
- 出版社重新设置字体、弦距、页眉页脚和版权信息；
- 网页转 PDF；
- 手机截图、裁剪和图片压缩。

因此出版物需要独立的“印刷谱”预处理，不应强行归入某个制谱软件。

## 适用的国际规范和开放标准

### MusicXML 4.0

- 官方定位：开放的数字乐谱交换格式。
- `<technical>` 元素支持吉他的 `<string>`、`<fret>`、`<hammer-on>`、`<pull-off>`、`<bend>` 等技术信息。
- `<fret>` 的 0 表示空弦，1 表示第一品。
- 适合作为识别结果与编辑软件之间的交换格式，但不能仅凭 MusicXML 恢复原始视觉排版。

### MEI

- MEI 是面向数字乐谱编码、学术出版和长期保存的开放模型。
- 具有专门的 `<tabGrp>` 六线谱分组元素。
- 更适合表达复杂编码和学术元数据，不适合作为第一版桌面应用的唯一中间格式。

### SMuFL

- 为现代音乐符号字体提供统一字形映射。
- Bravura、Leland、Petaluma、Gonville 等字体均遵循或接近 SMuFL。
- 可用于识别制谱软件和精确解释符号，但 SMuFL 不规定“X 在和弦谱中代表什么”这类版面语义。

### MNX

- W3C Music Notation Community Group 正在推进的新机器可读乐谱模型。
- 设计目标包括 Web、桌面和移动应用之间的交换。
- 当前仍在发展，不建议作为 toGp 唯一存储格式。

### GPIF / Guitar Pro 文件

- GP7/8 的 `.gp` 是 ZIP+XML。
- 能表达弦号、品位、技巧、和弦和布局。
- 适合作为 Guitar Pro 输出的目标格式。

### 记谱和出版规范

目前没有一个覆盖全世界所有六线谱出版物的统一 ISO 规则。不同出版社和制谱软件会在以下方面不同：

- 节奏符干放在六线谱上方还是下方；
- X、空弦 0、括号音和幽灵音的表示；
- 和弦图放在系统上方还是行间；
- 歌词、段落名和技巧文字的位置；
- 小节编号、反复记号和结尾的排版；
- 横按、推弦和滑音的图形表现。

工程上应使用：

1. 开放数据标准约束语义；
2. SMuFL 约束字形；
3. 来源适配器记录出版和软件习惯；
4. 原图对照与置信度处理未标准化差异。

《Behind Bars》等专业制谱规范可作为版面规则参考，但不应当作机器可解析的正式标准。

## 来源识别信号

### PDF 文件层

- `Producer`、`Creator`、`Title`、`Author` 元数据；
- 内嵌字体名称及子集名；
- 文本对象与路径对象比例；
- 每条弦线是文字字符、线条还是填充矩形；
- 页面尺寸和单位；
- 图片数量、编码和分辨率；
- PDF 生成时间与软件版本字符串。

元数据可以被清除、伪造或由系统和打印驱动覆盖，因此只能作为弱证据。

### 视觉层

- 五线谱与六线谱的相对间距；
- 弦数、弦距和音轨数；
- 小节线宽度和路径类型；
- 字体形状和字号层级；
- 颜色分布；
- 和弦图网格、指法点和横按；
- 歌词行数；
- 标题、作者、版权和页码布局；
- 技巧标记使用文字还是曲线。

### 内容层

- 小节编号连续性；
- 拍号和时值总和；
- 同音多弦候选；
- 和弦图与 X 的一致性；
- 重复、结尾和跳转记号；
- 页与页之间的调弦、轨道和谱表连续性。

## 推荐的软件架构

```text
文件/图片
  → 文件指纹
  → 渲染类型分类
  → 来源家族候选
  → 版面切分
  → 弦线/小节/文字/和弦分层
  → 来源适配器
  → 标准化 TabScore
  → 规则校验
  → 置信度与校对
  → GP5 / GP7/8
```

### 标准化 TabScore 应包含

- 来源：文件指纹、渲染类型、软件候选、置信度；
- 页面：尺寸、比例、变换矩阵、DPI；
- 系统：页面、轨道、弦数、调弦、X/Y 范围；
- 小节：边界、编号、拍号、重复、结尾；
- 事件：弦、品、时值、起拍、连接、技巧；
- 和弦：名称、图网格、每弦品位、横按；
- 文本：标题、作者、段落、歌词、说明；
- 证据：原图裁剪坐标、OCR 置信度、规则命中记录。

导出器只消费 TabScore，不在导出阶段重新解释图片。

## 验证与回归体系

每个真实来源至少准备：

- 原始谱面文件；
- 软件名称和版本；
- PDF 或图片输出；
- 手工校正后的标准结果；
- 来源识别期望；
- 弦数、小节数、音符数和和弦数期望值。

核心指标：

- 渲染类型识别准确率；
- 来源家族识别准确率；
- 系统数、弦数和小节数准确率；
- 音符弦号/品位准确率；
- 和弦名称与指法准确率；
- 时值准确率；
- GP5 能被 Guitar Pro 打开的比例；
- 每个文件的处理时间和峰值内存。

## 分阶段开发建议

### 阶段 0：样本库

先为 P0/P1 来源各收集 3–5 份代表性谱面，不立即开发所有适配器。

优先样本：

- Guitar Pro 8 导出的矢量 PDF；
- MuseScore 导出的矢量 PDF；
- TuxGuitar、LilyPond、TablEdit 的 PDF；
- Soundslice、Flat、Songsterr 的截图或打印 PDF；
- 中文流行吉他谱截图；
- 至少一份扫描出版物。

### 阶段 1：只做来源诊断器

输入文件，只输出：

```json
{
  "fileType": "pdf",
  "renderType": "vector_or_raster",
  "sourceCandidates": [
    {"family": "musescore", "confidence": 0.82}
  ],
  "features": {
    "textObjects": true,
    "embeddedFonts": ["Leland", "Edwin"],
    "imagePages": 0,
    "tabSystems": 8
  }
}
```

此阶段不改变转换结果，先建立可验证的分类基础。

本地诊断命令：

```bash
npm run inspect:score-source -- --pretty path/to/score.pdf
npm run inspect:score-source -- --pretty path/to/page.png
```

该命令不执行识别，也不会修改输入文件。

当前两个真实样本已经形成基线：

- “一直很安静”PDF：`vector-text`；5 页；无图片页；1830 个字符；4654 条线、253 个矩形、2582 条曲线；未命中已知软件品牌，标记为 `generic-vector-score`。
- “旅行的意义”截图：三页均为 `digital-raster-tab`；1400×1981、约 300 DPI；红色像素比例约 0.004；识别为 `digital-tab-screenshot`。

这些结果说明“来源品牌未知”不等于“无法建立稳定适配器”。版面和内容特征本身可以作为 profile 的依据。

### 阶段 2：通用版面分析

- 五线谱/六线谱分离；
- 弦数和小节线；
- 文本、歌词、和弦和符号分层；
- TabScore 中间模型；
- 小节编号与时间签名校验。

当前进展（2026-11-15）：

- 转换报告已包含版本化的 `tabScore`，记录输入来源、页面、谱表系统、轨道、调弦、小节和逐音弦号/品位事件；
- 谱表系统的版面坐标、小节边界与转换器的系统统计会合并到同一结构；
- 已加入谱表小节覆盖、轨道小节对齐、系统弦数、连续小节编号和事件范围校验；
- 校验问题会进入应用内的识别提示，但不会改变或阻断已成功生成的 GP5；
- 纯模型校验可用 `npm run test:tab-model` 回归。

### 阶段 3：高收益适配器

当前进展（2026-11-15）：

- 离线来源诊断与转换流程现在共用 `score_source_model.py`，避免两套分类阈值漂移；
- 转换报告的 `sourceDiagnosis` 记录渲染类型、来源家族候选、证据和每页视觉 profile；
- 适配器通过注册表选择，`sourceAdapter` 记录选中的适配器、来源家族、置信度和选择理由；
- 已注册通用回退、黑白水印六线谱、红色和弦数字谱和 MuseScore 矢量六线谱适配器；红色和弦适配器会记录和弦标签数、成功关联合成数、未关联合成数和 X→实际品位转换数；
- MuseScore 适配器依据 Creator 元数据和 Leland/Edwin 字体选择，并修正标题行中左侧轨道名与居中标题粘连的问题；
- 识别到 Guitar Pro 等已知来源但尚无专用规则时，仍明确显示来源候选并使用通用回退；
- 来源模型回归可用 `npm run test:models`。

按实际用户文件占比增加：

1. Guitar Pro；
2. MuseScore；
3. 中文数字截图/网页谱；
4. 扫描出版物；
5. TuxGuitar、LilyPond、TablEdit；
6. 其他商业软件。

### 阶段 4：校对与反馈

- 在原图上叠加识别框；
- 低置信度音符高亮；
- 音量、时值、弦号、品位修正；
- 修正结果进入回归样本；
- 不再靠开发者逐张人工猜规则。

## 关键风险

- PDF 元数据不是可靠来源标识；
- 品牌导出设置会让同一软件产生不同视觉输出；
- 截图和出版物无法反推出原始软件；
- X、幽灵音、空弦和闷音没有统一出版语义；
- 五线谱与六线谱同时出现时会互相误判；
- 技巧符号依赖 SMuFL 字体或路径形状；
- 仅靠通用 OCR 无法保证时值和声部；
- “支持所有软件”会无限扩大维护面，必须按样本覆盖率排序。

## 建议的第一版目标

第一版不要宣称识别所有软件。建议先声明：

> 支持 Guitar Pro、MuseScore 以及带有“红色和弦图 + 六线谱 X 占位”的中文数字谱，并提供通用矢量/扫描回退。

这个范围已经覆盖当前实际样本，同时保留扩展空间。
